# Train–Trackman 투구 매칭 전 과정 통합 보고서

기준일: 2026-08-20  
대상: `train.csv` 1,475,092행과 2019~2024 Trackman 이력  
목적: 각 Train 행에 동일 투구의 Trackman ID를 안전하게 연결하거나, 연결하지 못한 이유를 행 단위로 남기는 것

이 문서는 Trackman 원본 점검, 초기 행 단위 후보 분석, Train 경기 블록 생성, 경기 전체 수열 매칭, 삽입·삭제 허용 정렬, 강한·추가 검토·약한 후보의 후속 처리, 최종 행 상태와 검증 결과를 하나로 합친 최종 기준 문서다. 중간 보고서에는 당시의 임시 상태가 남아 있으므로, 최종 수치와 상태는 이 문서와 `train_match_status_enriched.csv`, `train_with_trackman_match_info.csv`를 우선한다.

## 2. 분석 원칙

이번 작업은 다음 원칙을 유지했다.

1. **Train 중심으로 판단한다.** Trackman에만 있고 Train에 없는 투구는 연결 대상이 아니므로 무시한다.
2. **같은 10개 상태값만으로 같은 투구라고 확정하지 않는다.** 경기 전체 수열, 앞뒤 순서, `pitch_no`, 투수·타자 변경 흐름까지 확인한다.
3. **Train에만 있는 행은 억지로 연결하지 않는다.** 실제 대응 행이 없다고 판단되면 매칭 불가 상태를 기록한다.
4. **값이 다른 replace 행에는 최종 ID를 부여하지 않는다.** 신뢰할 수 있는 후보 ID와 다른 컬럼만 별도 기록한다.
5. **모호한 후보는 보류한다.** 일부 행을 연결하지 못하는 것보다 잘못된 ID를 연결하는 것을 더 큰 오류로 본다.
6. **원본 파일을 수정하지 않는다.** 보정과 경기 블록은 파생 분석 파일에만 적용한다.
7. **Trackman ID를 재사용하지 않는다.** 하나의 Trackman 원본 행은 하나의 Train 행에만 최종 연결할 수 있다.
8. 사용자가 제시했던 별도 `trackman_data_audit`의 exact 경기 목록과 알려진 경기 수는 독립 경기 분석의 입력이나 정답으로 사용하지 않았다. Train 순서와 원본 Trackman에서 다시 계산한 뒤 결과를 비교할 수 있게 분리했다.

## 3. Trackman 원본 점검과 시간 순 정리

### 3.1 원본 형식 점검

원본 trackman_history.csv는 1,793,078행, 30컬럼이다. 모든 컬럼의 자료형, 결측, 범주값, 수치 범위와 날짜 표현을 점검했다.

`game_date`는 두 문자열 형식이 섞여 있었다.

| 원본 형식 | 행 수 |
|---|---:|
| `YYYY-MM-DD` 계열 | 956,963 |
| `/`가 포함된 날짜 형식 | 836,115 |
| 합계 | 1,793,078 |

trackman_history_sorted.csv에서는 모두 `YYYY-MM-DD`로 통일했다. 서로 다른 문자열이 같은 날짜를 가리키던 경우도 하나의 날짜로 정규화되어 고유 날짜 문자열 수가 1,059개에서 1,057개로 정리됐다.

투구 유형은 `ChangeUp`과 `Changeup`을 `Changeup`으로 통일했다.

| 컬럼 | 원본 `ChangeUp` | 원본 `Changeup` | 정규화 후 `Changeup` |
|---|---:|---:|---:|
| `tagged_pitch_type` | 170,859 | 225 | 171,084 |
| `auto_pitch_type` | 90,324 | 185,311 | 275,635 |

기존 결측은 임의로 채우지 않았다.

### 3.2 정렬 기준과 검증

Trackman에는 모든 투구의 실제 시각이 없으므로 서로 다른 경기 사이의 초 단위 전역 순서는 알 수 없다. 따라서 시간 순의 의미를 다음처럼 정의했다.

1. 경기 시작 날짜
2. `trackman_game_id`
3. 경기 내부 `pitch_no`
4. 같은 `pitch_no`에서는 원본 행 순서 또는 `trackman_id`

최종 경기 단위 매칭에서는 각 Trackman 경기를 `trackman_game_id`, `pitch_no`, `trackman_id` 순으로 정렬했다. 검증 결과 같은 경기 안의 `pitch_no` 감소는 0건이었다.

중복 `pitch_no`는 2개 키, 4행이었다.

- `20220907-LGMinor-1`, `pitch_no=126`
- `20230618-SKFuturesPark-1`, `pitch_no=207`

각 쌍은 `trackman_id`만 다르고 나머지 컬럼은 모두 같았다. 원본 행을 삭제하지 않는 원칙에 따라 정렬 파일에도 유지했으며, 최종 매칭에서는 `trackman_id`까지 정렬 키에 포함해 순서를 고정했다.

원본 `game_date` 기준 전역 감소 2건은 같은 시작일의 서로 다른 경기 사이에서 한 경기의 기록 날짜가 다음 날로 적힌 경우였다. 경기 내부 투구 순서 역전은 아니며, 전역 실제 투구 시각이 없는 데이터 한계로 관리했다.

이닝 감소 2건은 다음 원본 이상값이었다.

- `20210815-HanwhaMinors-1`: 6회에서 `inning=0`으로 감소한 뒤 다시 6회
- `20220417-DoosanMinors-1`: 3회에서 2회로 감소

이 값은 수정하지 않고 비정상 이닝 플래그 또는 Trackman 경기 수열 적격성 검사에서 제외 사유로 사용했다.

### 3.3 중간 투구 누락 추정 행

초기 `pitch_of_pa` 흐름 이상 26건을 행 앞뒤의 `pitch_no`, 타자, 타석 내 투구 번호로 검토했다. 그중 20개 전이는 중간 투구가 빠졌다고 해석하는 것이 자연스러웠다.

- 같은 타자이고 `pitch_no`와 `pitch_of_pa`가 함께 건너뛴 경우: 중간 타석 투구로 추정
- 타자가 바뀌고 다음 행의 `pitch_of_pa`가 2 이상인 경우: 새 타자의 첫 투구부터 역산

20개 전이에서 실제 빠진 `pitch_no` 수를 합치면 **24행**이어서 trackman_history_augmented.csv에 24개 추정 행을 올바른 경기·투구 위치에 추가했다.

- 원본 관측 행: 1,793,078
- 추정 보완 행: 24
- 합계: 1,793,102
- 같은 타자 사이 추정: 13행
- 타자 변경 구간 추정: 11행

추정 행에는 경기, 날짜, 이닝, 초·말, 투수·타자, 손잡이, 팀처럼 앞뒤에서 안전하게 추론 가능한 값만 넣었다. `balls_before`, `strikes_before`, `outs_before`와 측정값은 결측으로 유지했다. `is_inferred=1`과 `inference_reason`으로 원본 관측 행과 구분했다.

### 3.4 매칭용 정규화본

trackman_history_augmented_normalized.csv에서는 다음을 추가로 처리했다.

- `top_bottom`: `Top/Bottom`을 `T/B`로 변환
- 손잡이: 두 방향을 비교해 Train `1=Left`, `2=Right`를 선택
- 비정상 이닝: 수정하지 않고 `is_invalid_inning` 표시
- 비정상 카운트: 수정하지 않고 `is_invalid_count` 표시
- 카운트 결측: `is_count_missing` 표시

플래그 결과는 비정상 이닝 1행, 비정상 카운트 97행, 카운트 결측 24행이었다. 카운트 결측 24행은 모두 추정 보완 행이다.

중요하게도 이 보완·정규화본은 초기 행 단위 후보 분석에 사용했지만, 이후의 **독립 경기 단위 최종 매칭은 원본 `trackman_history.csv`의 관측 행만으로 다시 시작했다.** 따라서 최종 `trackman_id`에는 추정 행이 포함되지 않는다.

## 4. 초기 행 단위 10컬럼 후보 분석

경기 블록을 만들기 전에는 Train 각 행과 Trackman 각 행의 공통 10개 컬럼이 완전히 같은 후보 수를 계산했다.

```text
season
game_month
game_dayofweek
inning
top_bottom
balls_before
strikes_before
outs_before
pitcher_hand
batter_hand
```

추정 행과 비정상 이닝·카운트 행은 exact 후보에서 제외했다. 1행 후보, 앞뒤 문맥, 2·3·5행 연속 패턴까지 검사한 초기 결과는 다음과 같았다.

| 초기 행 단위 상태 | 행 수 | 의미 |
|---|---:|---|
| `confirmed_unique` | 104,900 | 10개 키 후보가 하나이고 앞뒤 문맥도 일치 |
| `ambiguous` | 1,345,513 | 후보가 여러 개이거나 문맥만으로 결정 불가 |
| `no_candidate` | 24,679 | 유효한 Trackman 관측 행 중 10개 키 완전 일치 후보 없음 |
| **합계** | **1,475,092** | |

이 방식으로 경기 전체 exact를 많이 찾지 못한 이유는 10개 컬럼이 선수나 날짜 ID가 아니라 경기 상태이기 때문이다. 예를 들어 1회초 0볼 0스트라이크 0아웃과 같은 상태는 수많은 경기에서 반복된다. 3행 창도 `123`, `234`, `345`처럼 겹쳐 검사했지만, 짧은 상태 수열이 다른 경기에서 반복되는 문제가 남았다.

따라서 이 단계의 `matched_trackman_id`, `trackman_matchability`, `match_status`는 초기 후보 실험의 레거시 결과로 보존하고, 최종 판단에는 사용하지 않기로 했다. 특히 초기 `no_candidate` 24,679행은 경기 수열 정렬 후 일부가 연결될 수 있으므로 최종 `매칭 불가`와 같은 의미가 아니다.


## 5. Train을 경기 블록으로 분할

Train에는 명시적인 경기 ID와 경기 날짜가 없으므로 원본 행 순서에서 경기 시작을 독립적으로 추정했다.

### 5.1 하드 경계 조건

다음 중 하나를 만족하면 새 경기 시작으로 보았다.

```text
첫 번째 행
또는 season 변경
또는 game_month 변경
또는 game_dayofweek 변경
또는 game_type 변경
또는 현재 inning < 이전 inning
또는 현재가 1회초이고 이전 행이 1회초가 아님
```

점수와 카운트는 경계를 직접 만드는 조건이 아니라 분할 결과 검증에 사용했다.

```text
start_state_consistent =
    inning == 1
    and top_bottom == T
    and balls_before == 0
    and strikes_before == 0
    and outs_before == 0
    and run_top_before == 0
    and run_bot_before == 0
```

### 5.2 최초 4,868블록과 한 행 보정

최초 분할 결과는 4,868블록이었다.

- 시작 상태 일치: 4,867블록
- 시작 상태 불일치: 1블록

불일치 원인은 `TRAIN_0709425`였다.

- 직전 행: 9회초, 점수 4-0
- 해당 행: 1회말, 카운트 0-0, 점수 4-0
- 다음 행: 9회말, 카운트 0-0, 점수 4-0

새 경기라면 점수와 주변 이닝이 설명되지 않으므로 이 행의 `inning=1`을 원본 오류로 판단했다. 파생 분석 파일에서만 `inning=9`, `top_bottom=B`로 보정하자 잘못 분리된 블록이 합쳐져 **4,867경기**가 됐다.

보정 후 4,867경기의 시작 상태는 모두 일치했고, 경기 내부 이닝 감소, 홈 점수 감소, 원정 점수 감소는 모두 0건이었다. 원본 `train.csv`는 수정하지 않았으며 최종 사용자용 파일의 원본 49개 컬럼에도 원래 값이 그대로 남아 있다. 보정값은 경기 분할과 수열 분석에만 사용했다.


## 6. 경기 전체 10컬럼 exact unique 매칭

### 6.1 Trackman 경기 수열 구성

독립 경기 매칭은 원본 `trackman_history.csv`를 사용했다. 각 경기는 `trackman_game_id`로 묶고 `pitch_no`, `trackman_id` 순으로 정렬했다.

- Trackman 전체 경기: 5,980개
- 10컬럼 수열 매칭 적격 경기: 5,954개
- 비정상 상태를 포함해 제외된 경기: 26개

다음 중 하나라도 있으면 그 Trackman 경기 전체를 exact 수열 후보에서 제외했다.

- 이닝 1 미만
- `top_bottom`이 `Top/Bottom`이 아님
- 볼 0~3 범위 밖
- 스트라이크 0~2 범위 밖
- 아웃 0~2 범위 밖
- 투수·타자 손잡이가 `Left/Right`가 아님

### 6.2 exact unique 조건

각 투구의 공통 10개 값을 하나의 토큰으로 만들고, 경기 전체를 토큰 수열로 표현했다. 다음 조건을 모두 만족해야 exact unique 경기로 인정했다.

1. Train과 Trackman 경기 행 수가 같음
2. 처음부터 끝까지 10개 컬럼 수열이 같음
3. 같은 전체 수열을 가진 Trackman 경기가 정확히 하나임
4. 같은 전체 수열을 가진 Train 경기 블록도 정확히 하나임

### 6.3 exact 결과

- 전체 Train 경기: 4,867개
- exact unique 경기: **2,574개**
- 해당 Train 행: **773,446행**
- 전체 수열 exact가 아니었던 경기: **2,293개**
- Train 경기 중복 연결: 0건
- Trackman 경기 중복 연결: 0건

`773,446행`은 각 행의 10개 상태가 전역적으로 유일하다는 뜻이 아니다. 경기 전체 수열이 양쪽에서 유일하고, 경기 내부 같은 순서의 투구끼리 대응하므로 행 단위 ID를 확정할 수 있다는 뜻이다.


## 7. exact 불일치 2,293경기의 삽입·삭제 허용 정렬

exact가 아니라고 해서 관련 Trackman 경기가 없는 것은 아니다. 양쪽 중 한 데이터에서 투구 한 행만 빠져도 이후 위치가 모두 밀려 경기 전체 exact가 깨진다. 이를 처리하기 위해 삽입·삭제를 허용한 수열 정렬을 수행했다.

### 7.1 후보 탐색 방법

1. `season + game_month + game_dayofweek`가 같은 Trackman 경기만 메타데이터 후보로 제한
2. 5행 연속 토큰 겹침으로 후보를 최대 20개까지 축소
3. `SequenceMatcher`로 equal, replace, insert, delete 구간 계산
4. 최고 후보와 2순위 후보의 일치율 차이 계산
5. Train과 Trackman의 미일치 행 수 계산

수열 일치율은 다음과 같다.

```text
수열 일치율 = 2 × 순서대로 일치한 10컬럼 행 수
               / (Train 경기 행 수 + Trackman 경기 행 수)
```

10개 중 일부 컬럼만 같은 행은 일치 행에 포함하지 않았다.

### 7.2 최초 경기 등급

| 최초 등급 | 조건 | 경기 수 |
|---|---|---:|
| 강한 정렬 후보 | 일치율 ≥ 0.995, 1·2순위 차이 ≥ 0.02, 양쪽 미일치 각 3행 이하 | 476 |
| 추가 검토 후보 | 일치율 ≥ 0.98, 1·2순위 차이 ≥ 0.01 | 991 |
| 약하거나 모호한 후보 | 위 조건 미충족 | 825 |

| **합계** | | **2,293** |

이 등급은 최종 행 상태가 아니라 후속 검증 우선순위였다.

### 15.2 레거시 컬럼 주의

상세 파일 train_match_status_enriched.csv에는 초기 행 단위 실험 컬럼도 남아 있다.

- `matched_trackman_id`: 초기 행 단위 후보 분석의 ID
- `trackman_matchability`: 초기 `confirmed/ambiguous/no_candidate` 계열 상태
- `match_status`: 초기 행 단위 상태

이 세 컬럼은 최종 연결 판단에 사용하지 않는다. 최종 기준은 반드시 `trackman_id`와 `trackman_match_status`다.

또한 `trackman_candidate_id`는 값이 다른 행을 검토하기 위한 잠정 후보일 뿐이므로 `trackman_id`처럼 사용하면 안 된다.

## 16. 해석상 한계와 사용 원칙

1. 최종 ID가 있는 행은 공통 10개 상태와 순서 검증을 통과했지만, Train과 Trackman의 모든 컬럼이 동일하다는 뜻은 아니다.
2. 최종 ID가 없는 행도 모두 같은 의미는 아니다. `후보 경기 불확실`, `값 불일치`, `후보 중복`, `Train 단독`을 구분해야 한다.
3. Trackman에만 있는 행은 Train 중심 목표상 결과 파일에 별도 연결하지 않았다.
4. 실제 투구 시각이 없으므로 서로 다른 경기 사이의 초 단위 전역 순서는 복원할 수 없다. 필요한 순서는 각 경기 내부 `pitch_no`다.
5. 24개 추정 보완 행은 데이터 구조 확인용이며 최종 Trackman ID 연결에는 사용하지 않았다.
6. 모델링에 Trackman을 사용할 때는 대회 규칙을 별도로 지켜야 한다. 현재 투구 이후 정보, 평가 데이터의 미래 행, 2025년 Trackman, 외부 데이터는 사용하면 안 되며, 필요한 경우 현재 투구 이전 시점의 안전한 누적 피처만 구성해야 한다.

## 17. 공유본의 범위

이 공유본은 최종 팀·선수 대응표 8개와 본문 보고서 3개만 포함한다. 실행 코드, 원자료, 중간 산출물, 개인 PC 경로는 공유 대상에서 제외했으며, 필요한 판단 근거와 최종 수치는 본 보고서 본문에 정리했다.

## 18. 최종 한 문장 요약

Train 1,475,092행을 독립적으로 4,867경기로 나눈 뒤 경기 전체 exact, 삽입·삭제 허용 정렬, 안정 equal 구간 검증을 차례로 적용해 1,275,274행에 중복 없이 Trackman ID를 연결했고, 나머지 199,818행도 후보 불확실·값 불일치·후보 중복·Trackman 대응 행 없음 등으로 전부 이유를 분류했다.
